# Claude 完成状态协议修复（2026-10-14）

完成标准：真实 CLI 的主任务完成后结束 Working（工作中）；停止检查被阻止、等待权限及子代理状态不提前结束；自动续跑重新计时。

## 证据和处理方案

用户指定的上次会话记录显示，005c8bc 曾只增加画面识别兜底，用户确认无效后由 f7cefb7 完整撤销。本次没有恢复那套结束词和耗时行推测。原截图文件已不存在；对应 Claude 历史中的版本为 2.1.296，结束时有 turn_duration（整轮耗时）记录。仅凭这些保留记录不能确定当时残留计时的启动入口。

Claude 官方[终端文档](https://code.claude.com/docs/en/terminal-config#see-session-status-in-your-terminal)说明：2.1.295 起支持 OSC 7501（程序状态协议）。只有终端回应能力探测，才会开始上报。协议[规范](https://www.superlogical.com/rex/docs/build/program-status)明确区分 working（执行中）、blocked（等待输入）、done（成功完成）、idle（无任务或中断）和 error（错误）；带 id 的记录属于子任务。

只读参考仓库 CHANGELOG.md 确认此功能。只读检查本机 2.1.296、2.1.299 的实际发布程序，也确认：排队或执行时为 working；真正成功后才为 done；停止和初始化为 idle。CLI 的 Stop（停止检查）钩子仍不是整轮成功信号。

当前代码缺失该协议处理，只能等待 Stop 候选和空闲画面。另有实际 Windows 传输问题：系统 ConPTY（伪终端）下，真实 2.1.296 虽发出了查询，但调试日志记录 `programStatus=no (probe: no reply to OSC 7501 ; ?)`；换用 node-pty 已随包提供的 ConPTY，在相同 CLI 和回复格式下立即收到主任务状态。分别核对 BEL 和 ST 两种终止符，根因在后端，不能只换回复终止符。

## 改动和历史保护

- 终端组件使用 xterm 的协议解析器回应探测并保存 Claude 主任务记录，兼容分片及两种终止符；子任务、其它程序和普通文本不替换主任务。
- 终端管理器按标签读取记录，释放终端时清理。
- 应用优先采用已接通的主任务状态；done 持续至少 2.5 秒且属于本轮时，沿用计时、通知、去重和自动提交入口。旧轮 done、blocked、idle、error 不被当作成功；working 可以启动自动续跑的下一段计时。
- 仅明确标记为 Claude 的 Windows 原生标签优先使用随包 ConPTY，加载失败保留系统回退；其它标签继续使用原后端。WSL 继续沿用已有隔离后端。
- 借鉴 b1e1406 的随包 ConPTY、首次尺寸和前端就绪保护；保留 9f5512e 对 Stop 后继续执行、权限弹窗、重复通知及续跑的防护。保留旧版 CLI 的原候选确认路径。
